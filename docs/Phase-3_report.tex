% ABSTRACT
\sectiontitle{Project Abstract (2 pts)}

\vspace{0.05cm}

\instruction{
(Brief restatement of your project's main goal. Max 300 words).
}

\vspace{0.12cm}

\answerbox{3.60cm}{{\small RouteRush is a C++17 system that takes a warehouse order from placement to delivery using classroom data structures and algorithms: a hash-map inventory, a priority queue with aging, a warehouse graph with Dijkstra, nearest-neighbour and 2-opt picking routes, fleet assignment and a delivery log. The aim is to cut urgent waits, late deliveries and picking distance versus FIFO and typed-order baselines. The backend was finished in Phase-II. In Phase-III we added a web dashboard with a 3D map of the Graphic Era warehouse and three Dehradun delivery points (ISBT, Clock Tower, Railway Station), where a user manages orders and stock, runs a policy, watches the routes and compares with FIFO.\par}}

\vspace{0.70cm}

% UPDATED APPROACH
\sectiontitle{Updated Project Approach and Architecture (2 pts)}

\vspace{0.05cm}

\instruction{
(Describe your current approach, including system design,
communication protocols, libraries used, etc.\\
Max 300 words).
}

\vspace{0.25cm}

\answerbox{4.75cm}{{\small Single-process C++17 backend using only the STL; CSV files hold products, orders and the layout. \textbf{Pipeline per order:} validate, plan picking route, plan vehicles, reserve stock (all-or-nothing), commit, log; a rejected order changes nothing. \textbf{Backend:} HashMap/Inventory, OrderQueue (heap with aging), Graph/RoutePlanner (Dijkstra, nearest-neighbour, 2-opt), Fleet, WarehouseManager. \textbf{Phase-III frontend:} browser (HTML, CSS, JavaScript, three.js for 3D) $\rightarrow$ HTTP/1.1 $\rightarrow$ JSON API (\texttt{Api}) $\rightarrow$ \texttt{Session} (validated lists of products and orders) $\rightarrow$ backend. A small threaded socket server (\texttt{HttpServer}) listens on 127.0.0.1 only and serves the pages (\texttt{StaticFiles}, path-checked). HTTP parsing, file serving and the API contain no socket code, so they are unit-tested in memory. Each run replays all orders on a fresh inventory and fleet, so inputs are never used up; the response includes every order's node-by-node route, which the browser animates.\par}}

% CHALLENGES
\sectiontitle{Challenges/Roadblocks (7 pts)}

\vspace{0.05cm}

\instruction{
(Describe the challenges that you have faced or are facing so far
and how you plan to solve them. Max 300 words).
}

\vspace{0.18cm}

\answerbox{4.05cm}{{\small \textbf{1. Toolchain:} the code needs C++17, but an old MinGW (GCC 6.3) failed on structured bindings and inline variables; we installed a current GCC (WinLibs) and put it first on PATH.\\
\textbf{2. Sockets:} the STL has none and Windows and Linux differ, so we kept them in one header. Browsers open idle connections that can stall a one-at-a-time server, so each connection gets a thread and one lock guards the state.\\
\textbf{3. Not live:} each run replays the whole order list; real-time mode is future work.\\
\textbf{4. Trade-off:} against the FIFO and naive-picking baseline, priority with aging cut URGENT wait from 82.0 to 17.5 ticks and late orders from 1 to 0, but EXPRESS and NORMAL waits rose 30\% and 51\%.\par}}
